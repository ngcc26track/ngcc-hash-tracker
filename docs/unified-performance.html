软件性能实测

主口径：不依赖专用密码指令，AMD Ryzen 7 7800X3D（Zen4），gcc 13.3.0 -march=znver4， taskset -c 0，64 KiB 长消息、512 位摘要、单线程单消息，取 rdtsc 周期中位数 ÷ 字节。 测量日期 2026-09-22。

征集面向的是通用商用密码杂凑标准，目标平台不能假定都带 AES / SHA 硬件扩展， 因此主排名建立在"只允许通用指令集"的条件上（§1）。允许密码指令的版本见 §3， 两者只差两行。

0. 五条结论

一、主排名前六依次为 CHIME 3.442、Megascon 3.668、Cuishen 4.617、ZC-DM 4.685、ZC-DMC 4.720、AXIS 4.787 cpb。 完整排名见 §1。

二、35 个候选里 32 个从一开始就不依赖任何专用密码指令。 这是编译验证过的： 把全部候选加上 -mno-aes -mno-vaes -mno-sha -mno-gfni -mno-pclmul -mno-vpclmulqdq 重新编译，34 个构建项里 34 个产出与原来逐字节相同的 .so（MD5 全部一致）， 只有 Pavelor 与 Wish 编译失败。对这 32 个候选，"禁用密码指令"的代价精确为零。 反汇编扫描也印证：全场只有 Pavelor（95 条 vaesenc）和 Wish（144 条）发射了密码指令， 没有任何候选使用 SHA-NI、GFNI 或 PCLMUL。

三、20 / 34 快于 SM3，23 / 34 快于 SHA3-512，10 / 34 快于 SHA-256，2 / 34 快于 SHA-512。 这组数字不依赖任何平台假设，是这批候选最稳的一条成果。

四、短消息上格局不同。 32 B 上长/短比 的跨度是 1.6 到 151.6（中位 4.5）：AXIS 从长消息第 6 掉到第 31（固定 1280 拍终结化）， ZC-DMC 第 5 掉到第 25；反向翻身的是 Duet（第 26 → 第 11）与 MasterCube（第 19 → 第 10）。 只看 64 KiB 的排名会掩盖一个量级的差异。 见 §4。

五、换编译器对名次的影响大于换 CPU。 同机同源码，gcc 13.3 换成 11.4， cpb 变化从 0.539×（MoFang 反而更快）到 2.645×（Dragon 慢 2.6 倍），中位 1.105； 而 XeonB 与 Zen4 之间的 cpb 比值中位 0.899、范围 0.581–1.107。见 §5。

2. Pavelor 与 Wish：这两个数字该怎么读

排在末两位的 Pavelor（127.830）与 Wish（3442.040）需要说明，否则容易被误读成"设计有多慢"。

能测到的只有参考实现。 Pavelor 的 Additional_Implementation/ 是空目录；Wish 交了五份实现， 四份优化实现（x86 性能/资源、ARM 性能/资源）全部依赖硬件 AES 轮——两份 x86 各 5 处 _mm_aesenc_si128，两份 ARM 合计 14 处 vaeseq_u8 与 14 处 vaesmcq_u8——只有参考实现不用。

参考实现是为可读性写的。 Wish 的 wish.c 只有 257 行，标准 AES S 盒查表加一个 4×4 MixColumns 矩阵逐字节做 GF 乘法；Pavelor 的参考实现同样逐轮调用一个 C 写的 aesenc()。 这类写法与认真做过的软件 AES 之间差一到两个数量级。

所以正确的结论是：这两家在"无密码指令平台"这个维度上没有提交任何证据， 127.8 / 3442 cpb 是其提交材料的上界而非设计的下界。作为参照，按每字节 2.375 个 AES 轮、 位切片 AES 轮约 115 门操作估算，Pavelor 的位切片实现应在 50–100 cpb 量级， 仍比表中前列慢一个数量级——这个设计的取向本来就是押硬件 AES，只是代价幅度拿不到实测支撑。

建议：若征集要求覆盖无密码指令平台，应要求这两家在第二轮补交位切片或查表优化实现； 在此之前，它们在本口径下的成绩不宜直接进入排名比较，只宜记为"未提交"。

三、AXIS 是最极端的一个：32 B 上 725.5 cpb，一次 32 字节哈希要 2.3 万个周期。 根因是它的终结化固定跑 1280 拍，与消息长度无关——长消息上摊薄到约 0.3 cpb 可以忽略， 短消息上就是全部成本。先前的分析还定位到其中约 80% 是实现层浪费 （axis_reupfull_constant_seq32 每次哈希做 10240 次逐比特提取，可完全预计算消除）， 但即使消掉，固定开销的量级不变。只看长消息排名会完全掩盖这一点。

四、在短消息上翻身的是 Duet、MasterCube、Thunder、uHash、LLH（Δ名次 +15 / +9 / +8 / +8 / +7）。 Duet 从第 26 升到第 11 尤其值得注意：它是押硬件的设计，长消息软件成绩垫底， 但每次调用的固定开销很低。

五、128 B 上格局又变一次。 FEILIAN 从 32 B 的 26.30 一路降到 128 B 的 6.47， Eijen 34.27 → 8.59，Vedak 46.75 → 11.73——这几家的固定开销在两三个分组内就摊掉了； 而 Thunder（15.56）、MasterCube（17.02）、XRH（43.6 / 42.2）在 128 B 上几乎不再下降， 说明它们的成本是按分组线性的，不是一次性的。评审若关心证书链、短报文认证这类场景， 应当直接看 64 B / 128 B 两列，而不是从 64 KiB 的排名外推。

读法：

  • 纯标量 ARX 型设计（Dragon、Thunder、Iphe）对编译器版本最敏感，名次在很大程度上是编译器的名次；
  • 手写汇编或 intrinsic 密集的设计（Pavelor 1.001、Wish、Cuishen、uHash、Litchi、Vedak）几乎不受影响——把代码写死反而带来跨工具链的可预测性；
  • MoFang 与 Wish 在旧编译器上更快，说明新版 gcc 的某些变换对它们是负优化。

流程建议：第二轮的自评估材料应强制声明编译器版本与完整编译选项。 目前各家自报值用的编译器五花八门（MSVC、MSYS2 gcc、Intel C++、未声明）， 在这个 4.9 倍的敏感区间里，不声明编译器的 cpb 基本没有可比性。

cpb 比值：XeonA/Zen4 中位 0.695（0.449–1.017），XeonB/Zen4 中位 0.899（0.581–1.107）。 cpb 上 Zen4 普遍吃亏，但 Zen4 跑在 4.19 GHz，换成 MB/s（不依赖频率假设的墙钟吞吐）后 Zen4 在多数项上领先。

排名本身相当稳：Zen4 与 XeonB 的名次差最大 ±4 位，头部（Pavelor / CHIME / Megascon） 与尾部（CHAMP / XRH / C Hash）在三台机上一致。需要担心的不是"换台机器排名就翻了"， 而是换编译器、或目标机器带不带专用指令。

两个例外值得记下：

  • ZC 三兄弟（ZC-DM / ZC-DMC / ZC-EDMC）在 XeonB 上明显更好（比值 0.58–0.65）， 是本对照里对微架构最敏感的一组非 AES 设计。
  • AFS-TrEDM 是唯一在 Zen4 上绝对吞吐也同时输给两台 Xeon 的候选，其 AVX2 hybrid 后端 在 Zen4 上没有产生预期收益，值得单独复查。

7. 全变体明细（云端 XeonB，124 个实现变体）

上面各表每个算法只取一个固定变体。要看"同一算法不同实现档位差多少"， 用的是另一份数据：35 个算法 × 124 个实现变体，全部通过 KAT_2_12 + 2_23 + 2_33 + Loop 共 4104 条向量的门槛（前面各表只过 KAT_2_12 的 4097 条）。

⚠ 这份数据的绝对值只有指示性：云端沙箱在几小时内会更换物理机，同一批二进制重测 可以差 0.48×–1.07×。但它是一次连续单机测量， 同一份数据内部的比值是可靠的，下面的结论都只用比值。

这些是提交完整性问题，不是设计问题。至少 6 个候选的名次被"没写向量化代码"拖累 （XRH-1/2、Neulaser、Laurus、Litchi、QILIN），3 个的自报数字来自包里不存在或未接入构建的代码 （Garnet、ZC-1536、Eijen）。

9. 局限

  1. 主口径的"禁用密码指令"是编译期开关加运行期能力屏蔽，不是在真实缺少这些指令的 CPU 上实测； 对通用 SIMD（AVX2 / AVX-512）的可用性假设仍然成立。
  2. 各算法取固定的一份实现（多为提交方的优化实现），不等于该算法的最优变体； 全变体明细见 §7。
  3. 只测 512 位摘要、单消息、长消息稳态。短消息见 cpb@32B 列——差异很大， AXIS 在 32 B 上是 725.5 cpb（一次 32 字节哈希约 2.3 万周期）、CHAMP 1141.6， 而 CHIME 只有 9.9——完整的短消息排名见 §4。多消息批处理未评估。
  4. 未做 ARM 平台测量。Wish 的 ARM 实现同样依赖 AES 扩展。
  5. Zen4 数据在两套独立的测试环境下复现， 32 项 cpb 比值中位 1.0003；云端数据不具备这种复现性，见 §7 的警示。
  6. 安全性与硬件不在本文范围。
